# risk-walkthrough：重难点实现说明

目的：代码太多无法逐行审核，所以只讲最需要人判断的部分，并检查有没有偏离方案。本 skill 只输出说明，不改代码。

## 篇幅

- 重难点不超过 5 处；偏离条目不超过 8 条。超出时，把次要的合并为一条“其他次要偏离”，逐条列出编号和一句话说明。
- 整份输出尽量控制在一屏半以内。细节需要时由用户追问，不要一次铺开。

## 步骤

1. **圈定范围**
   - 运行 `git status` 和 `git diff --stat`，列出本次改动的文件。
   - 只针对本切片的改动，不评论无关文件。

2. **选出重难点（3–5 处）**
   优先从以下类别中挑选，没有就不硬凑：
   - 事务边界、并发与锁、幂等
   - 权限与鉴权判断
   - 外部调用、降级、重试、超时
   - 跨模块交互（事件、模块间接口）
   - 复杂分支或状态流转
   - 数据库迁移与数据一致性

3. **每处重难点按下面的格式说明**
   - **位置**：`文件路径:行号`
   - **做什么**：3–5 句话描述实现逻辑（说明“为什么这样做”，不逐行翻译代码）
   - **不变量**：这段代码维护什么约束
   - **失败后的状态**：异常或中断时，数据和流程停在哪里
   - **替代方案**：考虑过但没采用的写法，以及没采用的原因
   - **测试覆盖**：由哪个测试覆盖；没有覆盖的要明确说明
   - **与方案流程的差异**：方案“关键流程”中有对应流程的，对照输入、关键步骤、失败状态和输出，列出不同之处；没有对应流程的注明“方案未写此流程”

4. **偏离检查**
   对照已确认的方案（若无已确认方案则注明），列出：
   - **真源核对（最先做，不得合并或省略）**：方案若规定某类数据或判定的权威来源在仓库之外或在另一处，检查本次改动是否在本地重新实现了同一判定或数据（自建映射、默认值、常量表、缓存副本等）。出现即为偏离，不能因为“功能能跑”而降级。
     - 检索方式：从方案的约束和“可复用的外部能力”中取出关键名词，在本次 diff 中搜索，逐处确认其来源。
     - 每处写明：本地实现的位置（文件:行号）、方案中该数据的真源（方案原文位置）、两者的差异。
     - 此类偏离单独列为条目，不计入“其他次要偏离”的合并数量。
   - **骨架核对**：对照方案的结构骨架，列出：骨架中有但代码中没有或位置改变的；代码中多出的模块、类型或接口；核心类型的字段或接口签名与骨架不一致的。方案没有骨架时注明“无骨架，按方案文字核对”。
   - 引入了“抽象与依赖预算表”以外的依赖或组件（第三方库、缓存、消息队列、新服务等）
   - 越出“非目标”的改动
   - 实现方式与方案不同之处
   - 切片边界变化：多个切片合并、拆分或调换顺序的，都算偏离
   每一项只能标注 **需要你决定** 或 **已在方案内**。
   - 只有方案原文明确写到的内容才能标“已在方案内”，并附方案的文件和行号。合并切片、调换顺序一律标“需要你决定”，不得因为用户曾口头同意就标“已在方案内”。
   - 用户口头同意过的偏离，写明“用户已口头同意（日期）”，仍标“需要你决定”，由用户确认是否记入方案。
   - 每个“需要你决定”条目只写三行：偏离是什么（一句话）、推荐选项（一个）、不选的后果（一句话）。不用选项对比表，除非用户要求展开。

5. **自检与未完成项**
   - 列出已运行的验证（编译、测试、静态检查等，命令以项目文档或构建配置为准）以及结果。
   - 未运行的验证要写明原因，不写“已验证”。
   - 声称“已修复”或“已通过”的，必须引用本次复跑的命令和输出；没有复跑就写“未复跑”。
   - 数字（文件数、行数、测试数、地址、版本号）必须来自命令输出或文件原文，不得凭记忆填写。涉及同一事实的地方前后必须一致；不一致时列出来让用户核对，不自行选一个。
   - 有遗留的 TODO 或已知缺陷，用 `TODO(issue)` 或 `FIXME` 标注后列出。
   - **未检查的地方（必填）**：列出本次没有验证的路径、分支、输入形态和环境（如未手工走过的界面流程、只有 mock 覆盖的外部调用、没测的异常分支），每条一句话写明没查的原因。确实都查过时写“无”，并列出依据的命令或测试。这一节交给 `quality-review`，独立审查优先覆盖这里。

## 输出格式

```
## 改动范围
## 重难点
### 1. <名称>（位置）
...
## 偏离检查
## 验证结果
## 未检查的地方
## 待你决定
```

“待你决定”按编号列出，每条只写问题和推荐选项，格式为“N. 问题 → 推荐：xxx”。全部列完后停止，不做修复。用户用编号回复（如“1 接受，2 改”）后，再按回复更新方案或代码。
